# Shifting one-page validation into resume-tailor, ahead of resume-packager

[ADR 0003](0003-resume-pdf-generation.md) gave `resume-packager` sole ownership of compiling and validating a resume's PDF, including its one-page limit — with one bounded retry that could trim overrun content. In practice that meant an overflowing resume was only ever discovered *after* `resume-tailor` had already finished and handed off, one full subagent dispatch downstream. The user wants overflow caught earlier: `resume-tailor` itself should not produce a `main.tex` likely to exceed one page in the first place.

`resume-tailor` now validates its own output before returning. After writing the tailored `.tex`, it compiles it via `pipeline.cli compile-resume-pdf` (the same deterministic function `resume-packager` uses) and checks the page count via `pipeline.cli check-resume-pdf` (passing no keywords — ATS coverage stays exclusively `resume-packager`'s concern). If the compile fails or the result exceeds one page, it gets exactly one fix-and-recompile attempt: fix a compile error introduced by its own edits, or trim the lowest-relevance content (oldest/least-relevant bullets first, then the summary) without touching a keyword it tracked in step 3. This mirrors `resume-packager`'s existing one-bounded-retry shape rather than inventing a new retry philosophy.

If that single attempt still doesn't produce a compiling, one-page result, `resume-tailor` reports it as an ordinary tailoring failure — the same contract it already uses for an unparseable resume or unusable job description. `/job-hunt`'s existing retry-once-then-record-as-failure handling (unchanged) already covers this: a second full `resume-tailor` dispatch gets a fresh attempt, and `resume-packager` is never invoked for a job that never produced a validated `.tex`.

`resume-packager` keeps its own page-count check as a backstop rather than dropping it — it's already compiling for the ATS check, so checking `pages == 1` at the same time costs nothing extra. It should now rarely fire for overflow specifically, since `resume-tailor` already guarantees it before handoff; its main remaining job is the ATS keyword check, with overflow as a defensive fallback (e.g. if `resume-tailor`'s shrink estimate and `resume-packager`'s own edits during its ATS-fix retry somehow interact badly). `resume-packager` always recompiles from scratch from the final `.tex` — it does not reuse `resume-tailor`'s validation-pass PDF. The two subagents stay fully decoupled: `resume-packager` doesn't need to know whether or how `resume-tailor` validated, and the extra `pdflatex` invocation is a cheap subprocess call, not an LLM-token cost.

## Considered options

- **Heuristic overflow estimate** (bullet/line/word counts) instead of an actual compile — rejected: real pagination depends on LaTeX spacing, hyphenation, and font metrics a heuristic can't see; this is exactly why a compile-based check already exists in `resume-packager`, and a second, less reliable mechanism would just add false positives/negatives.
- **Unlimited or multi-pass shrink loop** in `resume-tailor` — rejected in favor of a single bounded attempt, for consistency with `resume-packager`'s existing retry shape and to bound worst-case latency/compiles per job.
- **Hand off an overflowing resume to `resume-packager` anyway, relying on its retry to fix it** — rejected: this is the status quo being changed, and keeping it as the primary path would duplicate shrink logic across two subagents instead of giving `resume-tailor` clear ownership of its own output.
- **Reusing `resume-tailor`'s validation-compile PDF in `resume-packager`** (skip recompiling) — rejected: saves one cheap subprocess call at the cost of coupling the two subagents' file handling; not worth it for a compile step that costs no LLM tokens.
- **Dropping `resume-packager`'s page-count check now that `resume-tailor` validates it** — rejected: it's already compiling for the ATS check, so the backstop is free: a cheap safety net against `resume-tailor`'s shrink logic ever being wrong is worth keeping.

## Consequences

- `resume-tailor` needs no new tool access — it already has `Bash`, which is all `compile-resume-pdf`/`check-resume-pdf` require.
- `resume-tailor` now performs one extra `pdflatex` compile per job (two on the rare shrink/fix path) before ever handing off — more subprocess latency per job, but no additional LLM round-trips beyond the existing one-retry-at-the-orchestration-level pattern `/job-hunt` already has for tailoring failures.
- A resume that can't be made to fit one page now fails during tailoring rather than during packaging — `resume-packager` is never dispatched for it, and it's indistinguishable in `/job-hunt`'s reporting from any other tailoring failure.
- `resume-packager`'s behavior is otherwise unchanged: same compile-check-retry-report contract as ADR 0003, now expected to rarely trigger on the page-count branch specifically.
